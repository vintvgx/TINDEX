---
description: Pull open TODOs from the Daily Review backlog and implement them
---

Work through open TODOs from the app's Daily Review backlog (the `review_notes`
Supabase table, `kind = 'todo'`). Each TODO's `content` is a freeform request
written by the user (e.g. "add functionality to X") — treat it as a real task
description, not a code comment.

This is a **two-phase, plan-then-implement** workflow built around a markdown
plan document per day:

- **Phase 1 (plan):** for any open TODO that doesn't yet have a plan doc,
  write one outlining the intended approach. Don't touch code. Stop and tell
  the user to review it.
- **Phase 2 (implement):** for any open TODO that *already* has a plan doc
  from a previous run (so the user has had a chance to review it and add
  notes), confirm the approach with the user in chat — ask questions if
  anything in the plan or their notes is unclear — then implement, verify,
  update the doc, and mark the TODO done.

A single run typically does both at once: newly-seen TODOs get planned,
previously-planned TODOs get implemented (after confirmation).

Arguments: `$ARGUMENTS` — optional. A specific note id, a date (`YYYY-MM-DD`),
or a keyword/filter to narrow which open TODOs to consider. If empty,
consider all open TODOs across every date that has any.

## Base URL

Use the Railway backend the app is currently pointed at — check the
`ENVIRONMENT` constant in `mobile/lib/railway.config.ts` and use the matching
URL from `RAILWAY_URLS` (engineering: `https://alethia-test-eng.up.railway.app`,
production: `https://alethia-production.up.railway.app`). This is a
single-tenant personal app with no auth, so plain `curl` against these routes
works with no headers beyond `Content-Type: application/json`.

## Plan docs

One markdown file per `note_date`, at `docs/todos/<note_date>.md` (e.g.
`docs/todos/2026-08-13.md`). Each open TODO for that date gets its own
section, marked with an HTML comment carrying the note id so it can be
matched back to `review_notes` on later runs:

```markdown
# TODO Plan — <note_date>

Generated by /work-todos. Review the plan(s) below, add notes inline under
each TODO, then re-run /work-todos to implement.

---

## [ ] <short title> <!-- todo-id: <id> -->

**Requested:** <verbatim `content` from review_notes>

**Plan:**
- <step>
- <step>

**Notes:** _(add anything here before re-running /work-todos)_

---
```

When a TODO is implemented, flip its checkbox to `[x]` and add a **Result:**
line summarizing what changed (mirrors the `completion_note` sent to the
backend), leaving the Notes section intact for history.

## Steps

1. **Fetch open TODOs:**
   `curl "$BASE_URL/review/notes?kind=todo&done=false"`
   Filter/select by `$ARGUMENTS` if given (id, date, or keyword). Group the
   results by `note_date`.

2. **For each date group, read the existing doc first (if any)** at
   `docs/todos/<note_date>.md` *before* writing anything, and note which
   `todo-id`s already have a section in it. This is what distinguishes a
   TODO that's brand new to the plan-doc flow from one that's already been
   through a review cycle.

3. **New TODOs (no existing section for that id):**
   - Read the TODO's `content` and skim the relevant code so the plan is
     grounded, not generic.
   - Append a new section to that date's doc (creating the file if it
     doesn't exist) with a concrete, concise implementation plan. If the
     request is ambiguous, say so directly in the Plan section rather than
     guessing.
   - Do **not** implement these yet, and don't PATCH the note. They need a
     review cycle first.

4. **Previously-planned TODOs (section already existed in the doc on disk
   before this run):**
   - Read the full section, including anything the user added under
     **Notes** — that may add constraints, correct a wrong assumption, or
     approve the plan as-is.
   - Before writing code, confirm with the user in chat: summarize what
     you're about to do and ask any clarifying questions raised by the plan
     or their notes. If their notes already amount to a clear go-ahead for
     a specific, unambiguous plan, a brief confirmation is enough — don't
     force a question just to have one.
   - Once confirmed, implement using your normal engineering judgment — make
     the smallest correct change, follow existing patterns in the touched
     files. Don't expand scope beyond what the TODO (as clarified by the
     user's notes) asks for.
   - **Verify.** Run whatever is appropriate for what you touched (typecheck,
     relevant tests, lint). Don't mark a TODO done on unverified code.
   - **Record completion** — update the doc section (checkbox → `[x]`,
     add **Result:**) and PATCH the note:
     ```
     curl -X PATCH "$BASE_URL/review/notes/<id>" \
       -H "Content-Type: application/json" \
       -d '{"is_done": true, "completion_note": "<2-4 sentence summary of what changed, key files touched, and any caveats>"}'
     ```
     The server stamps `completed_at` automatically — don't try to set it
     yourself.
   - If, after reading the notes, the TODO is still too large/ambiguous to
     safely implement, leave it open and unresolved in the doc (checkbox
     unchecked) and flag it clearly in your final summary — don't force a
     half-finished change through.

5. **Skip TODOs whose plan section is already checked `[x]`** — already done.

## When done

Report a short summary grouped by date:
- **Planned (awaiting your review):** which TODOs got a fresh plan doc
  section this run, and where (`docs/todos/<date>.md`).
- **Implemented:** which TODOs were completed this run, with their
  `completion_note`.
- **Skipped/blocked:** which previously-planned TODOs still couldn't be
  safely completed, and why.
