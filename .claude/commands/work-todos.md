---
description: Pull open TODOs from the Daily Review backlog and implement them
---

Work through open TODOs from the app's Daily Review backlog (the `review_notes`
Supabase table, `kind = 'todo'`). Each TODO's `content` is a freeform request
written by the user (e.g. "add functionality to X") — treat it as a real task
description, not a code comment.

This is a **two-phase, plan-then-implement** workflow built around ONE
markdown doc, `docs/todos/OUTSTANDING.md`, that lists every open TODO:

- **Phase 1 (plan):** any open TODO without a section in the doc gets one
  outlining the intended approach. Don't touch code. Tell the user to
  review it.
- **Phase 2 (implement):** any TODO whose **Focus tonight** box the user
  has ticked (`[x]`) gets confirmed with the user in chat (ask if anything in
  the plan or their notes is unclear), then implemented, verified, recorded
  in the doc, and marked done. Unticked planned TODOs stay parked.

A single run typically does both at once: newly-seen TODOs get planned,
ticked TODOs get implemented (after confirmation).

Arguments: `$ARGUMENTS` — optional. A specific note id, a date (`YYYY-MM-DD`),
or a keyword/filter to narrow which open TODOs to consider. If empty,
consider all open TODOs across every date that has any.

## Base URL

Use the Railway backend the app is currently pointed at — check the
`ENVIRONMENT` constant in `mobile/lib/railway.config.ts` and use the matching
URL from `RAILWAY_URLS` (engineering: `https://alethia-test-eng.up.railway.app`,
production: `https://alethia-production.up.railway.app`). This is a
single-tenant personal app with no auth, so plain `curl` against these routes
works with no headers beyond `Content-Type: application/json`.

## The doc

Everything lives in `docs/todos/OUTSTANDING.md`. The per-date files
(`docs/todos/<date>.md`) are history only; read one if the doc links to it
for a fuller plan, but never create or update them.

Shape:

```markdown
# Outstanding TODOs

Generated by /work-todos on <today>. <how-to-use line: tick Focus tonight,
add Notes, re-run /work-todos>

| # | Added | TODO | Status | Size |
|---|-------|------|--------|------|
| 1 | <note_date> | <short title> | <New plan, needs review / Planned / Parked (why)> | <Small/Medium/Large> |

---

## 1. <short title>

**ID:** `<review_notes id>`

**Focus tonight:** [ ]

**Requested (<note_date>):** <verbatim `content` from review_notes>

**What exists today:** <grounded findings, file refs>

**Plan:**
- <step>

**Open questions:** <only if real ambiguity>

**Notes:** _(add anything here)_

---
```

The **ID** line is how sections match back to `review_notes`. Keep it a
visible line, not an HTML comment: markdown editors strip comments on save.
Keep the table in sync with the sections. Order open items newest first,
with parked items (user said skip/ignore in Notes) last.

## Steps

1. **Fetch open TODOs:**
   `curl "$BASE_URL/review/notes?kind=todo&done=false"`
   Filter by `$ARGUMENTS` if given (id, date, or keyword).

2. **Read `docs/todos/OUTSTANDING.md` first (if it exists)** before writing
   anything. Note which IDs already have a section, and which have
   **Focus tonight: [x]**.

3. **New TODOs (no section for that id):**
   - Read the `content` and skim the relevant code so the plan is grounded.
   - Add a section and a table row. If the request is ambiguous, say so in
     **Open questions** rather than guessing.
   - Do **not** implement these yet, and don't PATCH the note.

4. **Ticked TODOs (Focus tonight: [x]), or ones the user names in chat or
   in `$ARGUMENTS` as the ones to work on:**
   - Read the full section, including the user's **Notes**.
   - Before writing code, confirm with the user in chat: summarize what
     you're about to do and ask the plan's open questions that their notes
     don't answer. If the notes already amount to a clear go-ahead, a brief
     confirmation is enough.
   - Implement with the smallest correct change, following existing patterns.
     Don't expand scope beyond the TODO as clarified.
   - **Verify** (typecheck, relevant tests, lint). Don't mark done on
     unverified code.
   - **Record completion:** add a **Result:** to the section, change its
     table status to "Done <date>", and PATCH the note:
     ```
     curl -X PATCH "$BASE_URL/review/notes/<id>" \
       -H "Content-Type: application/json" \
       -d '{"is_done": true, "completion_note": "<2-4 sentence summary of what changed, key files touched, and any caveats>"}'
     ```
     The server stamps `completed_at` automatically.
   - On the next run, remove sections for TODOs that are no longer open
     (done ones drop out of the fetch). Their Result lives in the
     `completion_note`.
   - If it's still too large/ambiguous, leave it open, note why in the
     section, and flag it in the summary.

5. **Unticked, already-planned TODOs:** leave them as-is (refresh a stale
   file reference if you notice one). Don't implement.

## When done

Report a short summary:
- **Planned (awaiting your review):** which TODOs got a fresh section in
  `docs/todos/OUTSTANDING.md` this run.
- **Implemented:** which TODOs were completed this run, with their
  `completion_note`.
- **Skipped/blocked:** which ticked TODOs still couldn't be safely
  completed, and why.
